# 0002 — 改用户已有的文件，只在副本上改

- 状态：已采纳（`6809705` xlsx、`d6230ff` pptx；不变量见 DESIGN.md §15）
- 日期：2026-10-24

## 背景

`office/` 一直是「从素材生成新文件」：docx/pptx/xlsx 都是从零构建，PDF 有合并/拆分/
水印/表单。真正的工作文件——上周导出的讲义、自己的成绩表——只能读，不能改。
对照对象能改：docx 真实修订、xlsx 单元格、pptx 文字、PDF 表单扁平化。

## 决定

每个「改已有文件」的入口都写**新文件**，并且拒绝 `input == output`；原文件只读。
改动必须可清点：xlsx 回 `changed`（before → after，旧文本通过 sharedStrings 解回），
pptx 回 `slides`/`replacements`/`merged`，docx 回 `applied`/`skipped`。

实现手段是在 OOXML 上做**外科手术**，不是重新构建：

- xlsx：改 `<c>` 元素，保留 `s=`（样式索引）；文本写成 inlineStr，因此
  `sharedStrings.xml` 这张所有人共享的索引表从不重编号；公式不写缓存值，让 Excel
  打开时重算——否则改完输入旁边会显示一个陈旧的数字。
- pptx：只重写 `ppt/slides/slideN.xml`，其余部件逐字节复制；先在 run 内替换，
  跨 run 的短语才合并整段（并计入 `merged`，因为段内格式会丢）。

## 放弃的方案

- **用 rust_xlsxwriter 读进来再写出去。** 它只能创建。经过它一次，样式、合并单元格、
  条件格式、图片都会消失——对一个不能重新生成的文件，这是静默损坏。
- **跨 run 的替换直接拒绝。** 干净但没用：编辑器在每次格式变化和拼写检查处都会拆
  run，真实文件里「一句话」经常是两三个 `<a:t>`。所以合并，但如实计数。
- **允许原地保存（覆盖原文件）。** 少一步确认，多一条不可逆路径。写副本的成本是
  一次另存对话框。

## 后果

- 「文件即真相」的取舍延伸到二进制文档：数据库里不存在文档内容的第二个副本，
  索引可以随时重建。
- UI 必须能显示改动清单；否则「写成功了吗」只能靠打开文件确认。
- 三个格式各有各的坑（sharedStrings / run 边界 / tracked changes），共同契约只有
  两条：原文件不动、改动可清点。
