# 0003 — 手写 OOXML，不让模型写脚本生成文档

- 状态：已采纳（长期约束，非一次改动）
- 日期：2026-10-24

## 背景

Office 产出的两条路：让模型写 Python（python-pptx / openpyxl / pandas）跑出文件，
或者自己拼 OOXML。前者上手快、能力面宽；后者笨、每种格式都要单独啃。

对照对象选了前者（它的文档脚本引擎，自己也承认没有网络/文件隔离）。

## 决定

Cortex 手写 OOXML（docx/pptx 自建，xlsx 用 rust_xlsxwriter，PDF 用 lopdf），
不引入 Python 运行时，不让模型生成并执行脚本。

## 放弃的方案

- **模型写脚本 + Python 运行时。** 放弃的原因是**可测性**，不是安装体积：脚本的
  输出是模型的自由发挥，同一个提示两次运行可能得到不同的表格结构，回归测试无从
  写起；而 `office/` 现在的每条路径都是确定性的，测试能断言「这个公式在这里」
  「这处修订是真的 tracked change」。Cortex 整套证据纪律（引用冻结、答案五态、
  eval 采纳规则）都建立在「每一步都能解释、能回归」上，换一个不可测的出口等于把
  可测性让出去。
- **引入 Pandas 式自由分析。** 没有 Python 运行时；单元格编辑 + 公式已经覆盖
  「把这个数改掉、让汇总重算」这个真实需求，剩下的自由分析收益不抵成本。

## 后果

- 每种格式的能力边界由自己决定：docx 有 tracked changes 和边注，pptx 的版式是
  纯文本框（不依赖母版占位符，PowerPoint / WPS / LibreOffice 渲染一致），xlsx 有
  真公式和图表。
- 想加能力就得啃 XML，成本高但可预期；不想要的能力（脚本、插件、模板继承）不会
  被动带进来。
- 「改已有文件」也只能走同一套手术（见 ADR 0002），不能退回到「重新生成一份」。
