# 0001 — chat 流式：流是预览，答案是记录

- 状态：已采纳（`4ac82e7`，不变量见 DESIGN.md §14）
- 日期：2026-10-24

## 背景

`chat_answer` 在一次阻塞调用里跑完「检索 → 组织提示 → 生成 → 校验引用 → 落库」。
界面只能转圈，长回答的首字延迟等于全量延迟；所谓「打字机」只是把**已经存在的**
答案按 6 字/次放出来，看起来像流式，实际是把已经完成的工作重播一遍。

对照对象（SurfSense）在这一项上是服务端 run + SSE，可重放、可并发。这是与产品
定位无关、纯工程能力上的差距，也是唯一一条「对方明显更对」的。

## 决定

生成一次，观察两次：

1. 文字在模型还在写的时候就通过 `chat:delta` 事件离开进程（60ms 窗口 / 240 字上限
   合并，避免每个 token 一次 IPC、一次重渲染）；
2. 生成结束后，**后处理过的** `ChatAnswer` 才是记录——伪造的引用 token 被剥掉、
   答案五态被判定、引用被冻结——只有它落库。

因此气泡在答案到达时被**替换**，而不是追加。`chat_cancel` 置位一个 provider 在
chunk 之间读取的标志，被停下的答案状态是 `Aborted`（不是 `Truncated`：是用户结束的，
不邀请续写）。

## 放弃的方案

- **把流式文本直接写库，界面读库。** 看起来更「run 化」，但立刻有两个真相：预览里
  还有没被校验的引用 token，落库后又要改，历史里就留下一条从没被校验过的回答。
- **保留阻塞命令作为兜底路径。** 两条入口就是两条会漂移的管道（`retrieval_trace`
  已经因为「必须和 chat 同一条路径」被迫逐行镜像一次）；没人调的命令不发布。
- **只在主 provider 上做流式。** 选了 Claude 或走了 fallback 链的用户会看到
  「检索资料中…」挂满全程——对一个用户来说这就等于功能没做。所以 Claude 补
  `/v1/messages` + `stream: true`，fallback 链按实际服务的模型流式，且只在屏幕上
  **还没有字**时换 provider（有字再换会把开头打两遍）。

## 后果

- provider 的 `complete_stream` 从「可选优化」变成契约的一部分：默认实现（整段一次
  delta）只留给离线 stub 和忽略 `stream` 的端点，前端为它们保留打字机。
- 前端多了一个必须处理的窗口：请求返回前先订阅事件、按 `run_id` 丢弃过期 run、
  停止后不再把 delta 写进新气泡。
- 测试从「函数返回什么」扩展到「过程中发出了什么、按什么顺序、stop 之后还发不发」。
